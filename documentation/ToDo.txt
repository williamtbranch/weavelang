COPILOT AGENT — Runaway Prevention (deferred until after initial testing)
═════════════════════════════════════════════════════════════════════════
  Goal: prevent a confused copilot from cycling endlessly and burning tokens.

  1. Turn-limit enforcement
     - copilot_turns already tracked in state; max_turns already in CopilotConfig.
     - When max_turns is hit: stop executing CMD: lines, ask LLM for a summary,
       log summary to _journal.md, update _plan.toml statuses, enter paused state.
     - Terminal message: "[copilot] Session paused: turn limit (N) reached."

  2. Context compaction
     - When copilot_history exceeds a threshold (message count or estimated tokens),
       send the full history to the LLM with "summarize this context" instruction.
     - Replace history with the single summary message and continue.
     - Log compaction event in _journal.md.

  3. User reset commands
     - `$ reset`  — clear history, restart from _goal.toml (fresh session).
     - `$ resume` — continue after a turn-limit pause (resets turn counter).
     - LLM Settings dialog can also adjust max_turns and re-enable.

  4. Safety invariants
     - Turn cap enforced by WeaveLang Rust code, not the LLM — cannot be bypassed.
     - Compaction triggered deterministically by message count, not LLM decision.
     - Summary call is a bounded single request — cannot trigger further commands.
     - If summary call fails, log "compaction failed" and stop.

COPILOT AGENT WORKFLOW — FIXED
═══════════════════════════════
Problem: When an LLM agent (Copilot) runs translation stages via copilot.ps1, it needs
to wait for completion. The existing `watch_job` command blocks the HTTP relay's 30s
recv_timeout, causing 504 Gateway Timeout. The agent then resorts to polling loops in
the terminal which spawn background shells and get stuck indefinitely.

Root cause:
  - `watch_job` takes the llm_results_receiver and blocks in a loop until all items arrive
  - The relay server's HTTP handler has a 30s timeout on GUI response
  - LLM stages can take 5-30+ minutes → always exceeds timeout
  - Agent polling via `run_in_terminal` with loops spawns background terminals on timeout
  - No way to check progress without blocking

Fix (implemented):
  ✔ Added `job_status` terminal command (non-blocking, instant response):
    Returns "RUNNING 12/48 stage=GenerateAdvancedTarget tier=adv"
            "DONE 48/48 stage=GenerateAdvancedTarget tier=adv"
            "IDLE"
  ✔ Added `copilot.ps1 job_status` action — single non-blocking check
  ✔ Added `copilot.ps1 wait [interval_sec]` action — client-side polling loop:
    - Default 10s interval, 1-hour safety cap
    - Prints timestamped progress each poll
    - Exits cleanly on DONE or IDLE
    - Waiting happens in PowerShell, not in the HTTP handler

Agent workflow (new):
  1. .\copilot.ps1 cmd "run generate <Stage> <start> <end>"  → fire-and-forget, returns immediately
  2. .\copilot.ps1 wait 15                                    → polls every 15s, prints progress
  3. Proceeds to next stage when "DONE" is returned

  Or for manual checking:
  1. .\copilot.ps1 job_status                                  → instant status check

Design notes for agent-friendly commands:
  - Never block the HTTP relay for more than a few seconds
  - All long-running operations should be fire-and-forget + poll-for-status
  - Keep response text concise — avoid flooding LLM context windows
  - Status responses should be machine-parseable (prefixed: RUNNING/DONE/IDLE)
