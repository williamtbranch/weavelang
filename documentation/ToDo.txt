================================================================================
Project Plan: WeaveLang V8 - The Data Integrity Refactor
Last Updated: (Date of this session)
================================================================================

**Objective:** To perform a critical refactoring of the data pipeline and test suite to fix a fundamental data integrity issue related to the "Inverse Diglot" feature. This will ensure the Rust generation engine receives all the data it needs to function correctly.

---
**Part 1: The Core Problem Diagnosis**
---

A deep-dive debugging session has revealed a critical flaw in the data pipeline:

1.  **Missing Data:** The `inverse_diglot_map` in the final `stage10.json` files is structurally deficient. It currently exists as a simple map of `{ "spanish_word": "english_substitute" }`. It is **missing the crucial `spanish_lemma`** for each mapping.

2.  **Broken Engine Logic:** The Rust generation engine is designed to make substitution decisions based on whether a learner knows a specific *lemma*. Without the lemma present in the inverse diglot data, the engine cannot correctly determine if a substitution is valid. This is the root cause of the `NO_SUB` and other markers leaking into the final generated text from the L0 (AdvancedWeave) level.

3.  **Ineffective Pipeline Stage:** Stage 10 (`LemmatizeInverseDiglotMap`) was intended to solve this by finding the lemmas. However, the current JSON data structure provides no field to *save* the lemma it finds, rendering the stage completely ineffective. The data is calculated but immediately discarded.

---
**Part 2: The Action Plan**
---

To fix this, a coordinated, multi-step refactoring is required across the Python pipeline, the core Rust data types, and the Rust test suite.

**Step 1: Fix the Core Data Structure (The "Single Source of Truth")**

-   **File:** `src/types/json_types.rs`
-   **Task:** Redefine the data structure for the inverse diglot map.
    -   Create a new struct: `JsonInverseDiglotMapEntry { spanish_word: String, spanish_lemma: String, english_substitute: String }`.
    -   Change the `inverse_diglot_map` field in the `JsonAdvSpanishSegment` struct from `HashMap<String, String>` to `Vec<JsonInverseDiglotMapEntry>`. This will be the new, correct schema.

**Step 2: Fix the Python Data Pipeline**

-   **File:** `llm2books/stages/generate_inverse_diglot_map.py` (Stage 9)
-   **Task:** Modify this stage to produce the *new* data structure.
    -   It will parse the LLM's `spanish_word -> english_sub` output.
    -   For each pair, it will create a *partial* JSON object: `{ "spanish_word": "...", "spanish_lemma": "", "english_substitute": "..." }`. The `spanish_lemma` field will be intentionally left blank.
    -   It will write a list of these partial objects to the `stage9.json` file.

-   **File:** `llm2books/stages/lemmatize_inverse_diglot_map.py` (Stage 10)
-   **Task:** Modify this stage to correctly consume and complete the new data structure.
    -   It will now read the `Vec<JsonInverseDiglotMapEntry>` from the `stage9.json` file.
    -   It will iterate through the list. For each entry, it will use SpaCy to find the lemma of the `spanish_word`.
    -   It will then **update the `spanish_lemma` field** in that same entry with the result.
    -   It will save the final, complete `stage10.json` file.

**Step 3: Create a One-Off Repair Script for Existing Data**

-   **File:** Create a new standalone Python script (e.g., `repair_stage10_json.py`).
-   **Task:** This script is crucial for migrating all existing processed books.
    -   It will traverse the directory containing the final `.json` files.
    -   For each file, it will load the JSON.
    -   It will find the old, broken `inverse_diglot_map` (the HashMap).
    -   It will convert the old map into the new `Vec<JsonInverseDiglotMapEntry>` structure, using SpaCy on the fly to find and populate the `spanish_lemma` for each entry.
    -   It will overwrite the existing file with the new, corrected data structure.

**Step 4: Update the Rust Test Suite to Model Reality**

-   **Goal:** Create a test DSL that is unambiguous and accurately reflects the new, correct data structure.
-   **File:** `src/simulation/tests/generation_tests.pest`
    -   **Task:** Introduce a new, explicit tag for defining inverse diglot mappings within a segment: `(#inv-di <spa_word> <spa_lemma> <eng_sub>)`. This syntax is clean, provides all necessary data, and avoids confusion with the regular `#di` tag.

-   **Files:** `src/simulation/tests/weavetest_parser.rs` and `src/simulation/tests/test_generation.rs`
    -   **Task:** Update the test parser and compiler to understand the new `#inv-di` tag and populate the `DslSegment` and `NumericalAdvSegmentBundle` structs with the complete inverse diglot data, including the lemma.

**Step 5: Write the Final Failing Test Case**

-   **File:** `src/simulation/tests/generation_tests.weavetest`
-   **Task:** With the test suite fully upgraded, write the definitive test case that proves the `NO_SUB` bug.
    -   The test will force a fallback to a Moderate Spanish segment.
    -   The segment will contain an unknown lemma.
    -   The segment's inverse diglot map will map that unknown lemma to the `NO_SUB` marker.
    -   The `assert-text` will check that the engine correctly identified this as a failed path and fell back to the L1 `SimpleHybrid` level, producing the expected clean text from that level.
