### Primary Objectives & Guiding Principles

- **Goal:** Implement a smoother, more pedagogically sound learning gradient by refactoring the pipeline and engine to support a three-tier simplification model (Simple, Basic, Moderate).
- **Architecture:** The Python pipeline will produce these three distinct tiers of simplified text. The Rust engine will intelligently weave them together, prioritizing more natural prose as the learner's vocabulary grows.
- **Golden Rule:** The "jarring" stylistic gap must be eliminated. The learner's journey should be a gradual ascent from functional, deconstructed language to fluent, natural prose, before reaching the final, literary text.

- [ ] **Task 2.3: Fix the "Empty Mapping" Bug in the Phrase Mapper**
    - [ ] **Problem:** The current phrase mapper (`apply_phrase_mappings.py`) can generate invalid diglot map entries for phrases it fails to align, such as `[ 14, [], "", true, 3 ]`. This causes words to disappear from the final L1 text.
    - [ ] **Solution:** Modify the logic in `phrase_mapper_helpers.py`. When a multi-word "semantic atom" is invalidated (e.g., for crossing a segment boundary or containing punctuation), it must be correctly broken down into its constituent single-word tokens, and each token must be given a `NO_SUB`, non-viable mapping.

- [ ] **Task 2.4: Implement a New Semantic Validation Stage (Stage 4.5)**
    - [ ] **Problem:** LLMs can produce intermittently "shifted" or nonsensical phrase maps that are syntactically valid but semantically wrong. For example, in `LesMis` sentence `S18`, the LLM incorrectly mapped English `talk` to Spanish `creó`. Our current DP aligner is too robust and "self-heals" this, hiding the underlying data corruption.
    - [ ] **Solution:** Create a new pipeline stage, `ValidatePhraseMappings`, that runs after `ApplyPhraseMappings`.
    - [ ] This stage will use a free, local sentence-transformer model (e.g., `paraphrase-multilingual-MiniLM-L12-v2`) to perform cross-lingual semantic validation.
    - [ ] For each English phrase and its mapped Spanish phrase, it will calculate the cosine similarity of their vector embeddings.
    - [ ] **Validation Rule:** If a sentence contains a significant number of mappings with a similarity score below a defined threshold (e.g., < 0.3), the entire sentence will be flagged with a status like `RETRY_SEMANTIC_FAIL`.
    - [ ] The main pipeline orchestrator will be updated to handle this `RETRY` status, forcing the LLM to re-generate the failed sentence on the next run. This creates a self-correcting loop that guarantees the semantic integrity of our phrase maps.

- [ ] **Task 2.5: Refactor the Final Stage (FinalizeBook) for Lean Output**

    - [ ] This ensures the final JSON is as lean as possible for the Rust engine.
    - [ ] **Task 2.6: Implement Manual Validation Override (Future Enhancement)**
    - [ ] **Problem:** The semantic validator can have rare false-positives on short, idiomatic segments. We need a way to manually approve these without changing code.
    - [ ] **Solution:** Enhance the `semantic_validator` module.
    - [ ] It should scan the relevant LLM log file for special comments, e.g., `%%MANUAL_VALIDATION_PASSED: S127_S2%%`.
    - [ ] If such a comment is found for a given sentence/segment ID, the validator should automatically return `True` for that ID and log that it used a manual override.
    - [ ] This provides a robust mechanism for handling known-good edge cases in long pipeline runs without requiring code changes or relaxing the validation thresholds globally.
